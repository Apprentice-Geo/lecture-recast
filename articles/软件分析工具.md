# 软件分析工具

## 用软件改进制造软件的方法

软件是物理世界过程在信息世界的投影。人心里的意图（intent）、写下来的规格（spec）和最终实现（impl），并不会天然一致。软件工程所研究的，就是如何跨越这些距离，把「制造软件」变成一项有方法、有反馈的工程活动。

为此，我们积累了许多经验：人月神话提醒我们，增加人手不等于缩短工期；架构设计帮助我们控制变化；编码规范把反复踩过的坑变成规则。我们也发展出瀑布模型、敏捷开发等流程。不过，对软件开发者来说，最顺手的一条路始终是制造工具：版本管理、IDE、编译器、编程语言、框架、调试器，都在改变我们制造软件的能力。

回望这段历史，可以把它看成一种「人类 RSI」。RSI 是 Recursive Self-Improvement，即递归式自我改进：我们不仅做事，还改进做事的方法，进而改进「如何改进」。软件工程离软件开发者如此之近，构造软件来改进软件，实在天经地义。这里的「自我改进」并不意味着工具会自动进化；过去主要是人发现问题、设计工具，再利用工具获得更强的开发能力。

到了 AI 时代，这个循环里的一部分也可以交给 Agent。一次任务中写出的检索脚本、失败复现器和实验工具，可以成为下次任务的基础设施。值得思考的就不只是「AI 能否写出这一段程序」，还有「它能否把这一次摸索，变成以后不必重复摸索的工具」。反馈怎样获得、工具怎样验证、经验怎样保留，会决定这个循环是否真的在改进。

在生成式 AI 之前，传统软件分析工具大体是「机械」的：人必须先把意图变成明确的规则，工具才能执行。即使是通用框架，也需要配置或编程。检查器回答某条规则是否满足，IDE 根据语言结构做补全和重命名，调试器展示执行状态。这些工具围绕语法或形式语义工作，而「这段代码符合人的真实目的么」，通常仍要由人来回答。

## 把程序作为数学对象

在向 AI 许愿的同时，不要忘记 Computer Science 的根基。给定执行语义和所需的环境条件，程序的运行可以像单步调试器那样描述：当前状态是什么，执行哪条语句，下一步变成什么状态。涉及输入、并发和外部环境时，也要把相应选择纳入描述。正因为执行有明确的规则，我们才有可能把程序作为数学对象研究。

测试、分析和验证，从不同方向利用这个根基。测试选择具体输入，执行程序，再通过预期输出或应当满足的性质判断结果；这里负责判断对错的依据通常称为 oracle。分析则试图从代码推导可能的行为，例如不逐个枚举变量的取值，而是跟踪「它始终处于某个区间」。验证进一步把规格变成证明义务，要求说明在给定假设下，所有相关执行为什么满足性质。

但不能因此期待一个「验证一切程序」的算法。Rice 定理揭示了通用程序语义判定的根本限制：对一般程序，不存在一个总能终止、又能正确判定任意给定非平凡语义性质的万能方法。这里的非平凡，是指该性质并非对所有程序都成立，也并非对所有程序都不成立。这不是说某个具体程序无法被证明，而是说不能指望同一种算法包办所有情况。

考虑下面的程序：

```python
for a, b, c, n in all_positive_integer_tuples():
    if n > 2 and a**n + b**n == c**n:
        abort()
```

假设枚举器最终能枚举到每一个正整数四元组，运算使用数学意义上的整数，不受机器资源限制，那么「它永远不会执行 `abort`」恰好对应费马大定理。几行代码，就能装下一个极其困难的数学命题。我们今天知道这个命题有证明，却不能据此制造一个能解决所有类似问题的判定器。

工程上的回答是：既然没有银弹，那就做取舍。限制程序，限制性质，限制输入，或者允许工具回答 unknown；也可以接受一定的误报或漏报。重要的是，这些取舍能否换来对软件工程有用的结果。

## 每一种工具保留了什么，又忘掉了什么

类型系统保留值的类型和结构，把许多不合法操作排除在执行之前。普通类型没有表达的具体数值、调用时序和业务要求，仍然需要别的办法处理。它的项目知识来自声明和标注；检查通过，意味着排除了类型系统所覆盖的一类错误，失败则通常能定位到类型不匹配的位置。

Linter 根据语法模式和配置规则寻找可疑代码。它适合把团队约定和常见错误机械化，却不能把「符合规则」直接升级为「业务正确」。一条告警也可能在当前场景下不适用。抽象解释则用区间、正负号等抽象值描述程序状态，用可计算的近似代替庞大的具体状态空间。如果分析保持健全性，也就是没有遗漏假设范围内可能发生的行为，那么排除危险状态就能给出相应保证；代价是近似可能把实际不会发生的行为也算进去，产生误报。

执行类工具选择另一种取舍。单元测试保存选定输入和预期输出，通过意味着这些案例没有回归，失败则留下一个明确的例子。Fuzzing（模糊测试）自动生成或变异输入，配合 Sanitizer 等运行时检测工具发现崩溃、越界等问题。它依赖测试入口、输入格式和运行环境：没有执行到的行为不会自动获得保证，未编码的业务意图也不会凭空成为判错依据。它最有价值的产物之一，是一个可以反复运行的触发输入。

Property-based testing（基于性质的测试）把关注点从一组指定答案移到一条一般性质。例如，对合法数据编码再解码，应当恢复原来的内容。生成器决定测试能看到哪些输入，性质决定它能识别哪些错误；失败后，工具还可以尝试缩小输入，留下更容易理解的反例。通过大量采样会增加信心，但并不等于穷尽输入域。

当独立的标准答案难以得到时，还可以使用差分测试和蜕变测试。差分测试比较多个实现的结果；蜕变测试检查输入经过某种变换后，输出是否仍满足预期关系。前者需要可信的对照关系，后者需要我们提供正确的变换性质。相互一致是一种证据，但多个实现也可能共享同一个错误；发现不一致，则往往还需要判断究竟是谁出了问题。

模型检验把系统表示为有限状态模型，检查模型内的全部相关行为，失败时可以给出一条反例轨迹。它的保证属于这个模型，模型省略的数据和实现细节，需要另外解释。符号执行用符号值代替具体输入，沿路径积累约束，进而寻找满足约束的触发输入；实际使用时，未探索的路径和简化的环境依然构成边界。定理证明则在明确的规格和假设下建立逻辑保证，但形式化规格与真实需求之间的距离，并不会因证明完成而消失。证明目标没有完成，也不一定说明程序有 bug，可能只是还缺少引理、模型或合适的证明方法。

因此，看到绿色对勾，我们应该问：它究竟买到了什么？看到红色告警，我们应该问：它究竟留下了什么？一个可复现输入、一条反例轨迹和一个未完成的证明目标，代表不同的证据，也决定了不同的下一步。

这些工具让看起来「完全黑盒」的软件变得可以观察、可以质疑、可以改进。老师开玩笑说，看到不一致的缩进、空格和一堆不加管理的生成文件，为什么会血压升高？因为它们增加了「维护者不会写代码」的信心。如果连基础工具都没有用好，很难相信更复杂的质量保障已经到位。这不是用排版证明代码有错，而是在强调：工程习惯本身也在不断释放信号。

## 把程序作为概率分布的采样

传统工具的基本假设是：人先写规则，工具再照着做。我们当然可以用 AI 替换工具中的某个部件，让它选择更好的测试输入，或给告警排一个更好的顺序。但还有一个更大胆的视角：为什么不能把软件本身看作某个概率分布采样出来的结果？

这并不是说，确定性程序的下一条指令忽然随机了。它讨论的是代码如何产生：人在某种需求、上下文和编程习惯下写出代码，代码因此携带了关于这些背景的线索。程序既是形式化执行的对象，也是人类活动留下的样本。

先看两段匿名代码：

```python
def f(x):
    return not x.foo(c1) and x.bar >= c2

def f(x):
    return x.foo(c1) and x.bar <= c2
```

仅凭这些表达式，不能判断哪一个符合需求。两者都可能在某个规格下正确。现在恢复名字和常量：

```python
def can_watch_huang_guo_tv(visitor):
    return not visitor.inside('China') and visitor.age >= 18

def can_watch_huang_guo_tv(visitor):
    return visitor.inside('China') and visitor.age <= 18
```

突然之间，布尔运算连接到了人的世界：访问者在哪里、年龄是多少、能不能观看某个平台。第一段允许中国境外且年满 18 岁的访客，第二段允许中国境内且不超过 18 岁的访客。地区条件和年龄方向都值得追问。即使还不知道平台的真实政策，我们也已经知道应该去核对什么，而不是只检查表达式是否符合语法。

名字提供了意图线索，却不自动成为需求的权威来源。这个课堂例子的重点，也不是宣布平台采用哪一种访问政策，而是展示同一段形式结构在接回上下文之后，如何获得人能理解、能质疑的意义。软件同时承载着人类需求的对齐和形式化世界的执行，过去工具很难跨越的距离，现在有了新的连接方式。

我们希望检查的是：对于形式化世界中的 execution trace，也就是执行轨迹，把它「翻译回人类世界」之后，行为是否符合 intent 和 spec？可以把这个目标称为 informal verification，非形式化验证。这里的「验证」表达的是希望完成的任务，并不意味着 LLM 的判断已经具有数学证明的保证。

例如，模型怀疑年龄条件写反了，接下来可以构造不同年龄和地区的访客，运行代码，记录谁被允许、谁被拒绝，再把这些具体行为与需求对照。「我觉得不对」因此有机会变成具体输入、执行证据和一条需要澄清的意图。这比只让模型笼统评价「代码质量不错」有用得多。

## 策略交给模型，机制仍然关键

老师用一句改写的口号表达这种变化：

> Heuristics is dead, Policy is Heuristics, LLM is Policy, Mechanism is King.

Heuristics 是启发式方法，Policy 是决定做什么的策略，Mechanism 是让事情能够执行的机制。可以把它理解为：过去写死在工具里的部分经验策略，如今可以交给模型；模型决定查哪里、追问什么、如何理解观察结果，而工具必须提供可靠的观察、执行、控制和重放能力。

这句口号当然不意味着启发式算法真的全部消失。它强调的是研究问题的变化：如果只是给旧工具加上 LLM，把某个指标提高一点，我们可能没有用足新能力。更值得追问的是，工具能不能第一次检查那些「很难写成规则，但人知道不对」的东西。

课堂举到的一个早期方向，是从大量系统日志中学习正常运行的模式，再寻找偏离模式的异常行为。相关工作可参见 [Detecting Large-Scale System Problems by Mining Console Logs](<https://dl.acm.org/doi/10.1145/1629575.1629587>)。这提供了一个出发点：不必先为每一种故障手写完整规则，也能从运行记录中寻找可疑之处。不过，少见不等于错误，常见也不等于符合需求；异常信号仍需要解释。

进一步设想，如果每条语句都留下日志，能否从轨迹中恢复一种 informal semantics，即面向人类理解的非形式化语义？工具不仅指出「这条轨迹和其他轨迹不同」，还尝试说明「这个用户请求为什么没有得到应有的处理」。这是一个探索方向，尚不能仅靠增加日志就宣称实现；日志是否充分、上下文是否完整、解释如何核验，都是问题。

同样的变化也会发生在软件视图上。调试器不必只展示变量名和十六进制地址。[DDD 图形调试器](<https://dl.acm.org/doi/10.1145/249094.249108>) 所代表的方向，是把数据结构投射成人可以查看和探索的图。今天，我们可以进一步设想让模型根据任务组织视图：追踪某个请求经过哪些状态，解释对象之间的关系，突出某次执行中真正相关的变化。模型帮助选择呈现方式，底层机制则负责提供真实状态，允许人回到证据。

沿着这个想法，「no doc」也许有了新的含义。能够从代码可靠提取的结构和行为，可以按需解释，不必总是再维护一份容易过期的副本。真正需要长期记录的，是代码里提取不出来的信息：为什么选择这个需求，为什么放弃另一种方案，某个看似奇怪的约束来自哪里。模型可以帮助读代码，却不能可靠地从结果反推出所有历史理由。

## 软件工程工具的未来

软件生成面临三个彼此相关、又不相同的目标：语法正确、语义正确、阅读自然。语法制导的搜索可以约束候选程序的结构；语言模型擅长生成看起来像人写的代码。但能编译、读着顺，并不等于实现了我们想要的功能。语义正确始终需要一个参照：究竟相对于哪一份需求和规格？

这个开放问题解决了吗？课堂给出的判断是：一定程度上，可以靠不断试错、调用更多工具来诊断和修复，但过程可能相当低效。这里依靠的，仍然是人类工程师长期积累的软件工程经验和工具。AI 把它们组织进一个自动循环，并不意味着那些经验背后的困难已经消失。

尤其要注意架构失败。一个补丁让当前测试通过，却也可能增加新的耦合；下一次改动就要理解更多例外，跑更多验证，再打更多补丁。系统最终可能陷入无法维护的泥潭。单次修复成功和持续演化能力，是两种不同的质量。

因此，反馈不能只覆盖眼前的功能，还要覆盖未来修改的代价。一个值得尝试的工具设想是：让 Agent 在隔离的分支中演练一次合理的需求变更，观察修改波及哪些模块、打破哪些假设、需要重做哪些验证。演练不自动证明架构优良，却能把「这里以后恐怕难改」变成可讨论的证据，再据此调整模块边界、保留设计理由。

制造下一代软件工程工具，需要同时抓住两个世界：利用程序作为数学对象时可以检查的确定性，也利用程序作为人类活动产物时携带的上下文。让模型提出有意义的怀疑，让工具把怀疑变成可以执行和核验的反馈，再让反馈改善下一轮开发，这才使「用软件改进软件」获得了继续向前的可能。
